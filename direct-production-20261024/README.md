# Direct production and in-place digest use — experimental EPYC screen

October 24, 2026. EPYC 9255, Linux; four relinked layouts per implementation,
eight alternating pairs through bench-hashes regress/compare. All runs are
experimental; do not import them as the published benchmark's usual cells.
The samples carry an `experiment` header and the report labels this workload.

## Exact setup

Library 0627c0c38309a9e68ecf51ca1764978a67c6cb3d:
- Devon output-parameter experiment f503409;
- opt-in GPR single-chunk prototype (same body as 218b3bc);
- Stream ring alignment from #144, identical on both sides.
Normal builds use SIMD. `BLAKE3_DIAGNOSTIC_GPR=1` substitutes GPR arithmetic only
for the AVX-512-selected single-chunk root call; wide batch kernels are unchanged.

Benchmark d87f18ad70b55f5d53fe553bb4ff93a2139d642d, feature `diag-direct-flow`:
- Devon's batch alignment and heap-output API experiment;
- persistent per-thread output slot correction (for the preceding experiment);
- separate `src/direct_flow.rs` for this direct producer/consumer model.
No global aligned allocator is used.

The producer calculates each 64-bit word from sequence and word index, then
stores it directly into the final aligned input buffer (or Stream ring room).
There is no source message to copy. The consumer reads all 32 output bytes from
the caller's heap output slot and folds them into a scalar checksum. It does
not call the ordinary benchmark's digest-copy sink.

The synchronous single-message case feeds that checksum into the next input's
seed: it needs each answer before the next message can be produced. Batch and
stream messages are independent. These are end-to-end costs including generation,
hashing and in-place consumption; they are not isolated compression timings.

- ST single/batch: affinity CPUs 0,2 (two physical even cores; each solo sample
  uses its calling thread, the two shared copies can use separate cores).
- Stream: CPUs 0,2,4,6, four participants (`--threads 4`). One stream per sample,
  setup/draining/free-place bookkeeping included. Outputs reused as delivered.
- Streams' ns/message are throughput costs, not time to delivery of one message.
- Tests: library GPR 108/108; diagnostic benchmark 49/49 with SIMD and 49/49 GPR.
  Tests check generated bytes, output correctness, stable storage, and actual
  Stream ring-room alignment through producer callbacks.

## Results: SIMD -> GPR

Numbers below are the solo cells. The full comparisons retain the shared cells
and positive means as well. Cost reductions, not throughput multipliers.

| Workload | SIMD | GPR | Paired cost judgment |
|---|---:|---:|---|
| dependent single 64 B | 88.3 ns/message | 68.2 ns/message | -22.7%, faster, 8/8 |
| dependent single 256 B | 1.262 ns/B | 0.983 ns/B | -22.2%, faster, 8/8 |
| dependent single 1 KiB | 1.247 ns/B | 0.958 ns/B | -23.2%, faster, 8/8 |
| batch of 16 x 64 B | 8.174 ns/message | 8.230 ns/message | +0.7%, level |
| batch of 64 x 64 B | 7.587 ns/message | 7.573 ns/message | -0.2%, level |
| batch of 256 x 64 B | 7.643 ns/message | 7.600 ns/message | -0.6%, level |
| stream of individual 64 B | 19.7 ns/message | 17.9 ns/message | -9.2%, level, 5/8 |
| stream of batches of 64 x 64 B | 4.038 ns/message | 4.036 ns/message | level |

Stream individual 256 B and 1 KiB solo means fell 7.8% and 15.4%, both level.
Shared individual-stream means rose 7.7% (64 B), 1.9% (256 B), and 9.3% (1 KiB),
also level. Thus there is **no established stream win** and no equivalence claim.

### What actually ran

Separate perf profiles are diagnostic only, never used for the speed verdict:
- single 1 KiB: 85.5% of samples in GPR chunk-root;
- batch 64: 78.5% in existing `blake3_hash_many_avx512`;
- individual-message stream: 40% pool serve, 24% add_part, 14% wide hash_many;
- batch stream: 62.5% wide hash_many.
The integer single-chunk kernel does not replace those efficient wide batch
paths. Queue/dispatch work dominates much of the individual-message stream.

Static disassembly of the direct single-message loop shows 8-byte generated
stores, a call of hash_serial with the heap output pointer in r8, then loads
from that same output and checksum reduction. There is no message memcpy or
32-byte digest copy in the loop. Setup/map growth may still allocate or move
metadata before calibration; this is not a claim that the whole process makes
no copies of any kind.

### Why 64 B differs from the preceding experiment

The earlier aligned-input, persistent-heap-output **copy-in** experiment found
GPR 14.3% slower at 64 B and 22.1% faster at 1 KiB. The direct producer changes
64 B to a win. Its generated 8-byte stores differ from memcpy's stores; narrower
GPR loads can have different forwarding behaviour from SIMD loads. This is a
plausible explanation, not an isolated proof of the cause. The workload also
uses a dependency chain and a different consumer. Removing caller copies does
not imply that every possible producer or consumer gives these same gains.

No Intel or Zen 6 performance claim follows from this one-host screen. No
production dispatch has been changed.
