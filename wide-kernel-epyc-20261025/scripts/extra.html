What was compared

  • Old: John's candidate/release-0.8 0754066 (servil main, plus the 0.8 integration: #164 kernel names, the two kinds of call, the proofs), with Devon's FANOUT 8 waker (485d7ab), the best waker measured on this machine: commit a9e70b8. John's servil branch (a92c97d) itself can't be measured fairly: it predates #164, so a bench binary would run official BLAKE3's batch kernels in its place (#151). Its 15 extra commits are documentation only.
  • New: the same, plus the 32-input AVX-512 chunk kernel, its 16-input parent kernel and its tree-thread budget, ported from a5e1e18 (October 23-24) with only the symbol names changed (the generated assembly is byte-identical otherwise): a49ff2c, branch experiment/sam-wide-on-0.8.
  • Ablation: the new kernel without the tree-thread budget, 433502a (measurement only).
  • EPYC 9255 (Zen 5, 24 cores, 48 threads), Linux 7.0.0-38, rustc 1.99.1, governor performance, under the bench lock, nothing else running. bench-hashes d21cdf36 on both sides. All timing and statistics come from the existing check/regress/compare/b3sum; SMT and energy come from perf.
  • Correctness on this machine (both sides): release 123, debug 124, pure 106, no_std 34, C API 8, doc 19, Shuttle 7, proof helpers 34, b3sum, check-builds: all pass. The new side's run includes the wide kernel's guard-page tests, the dispatch tests, and the startup self-test with its corruption test.

Major pros and cons

ProsCons
About 20% less time for one thread hashing bulk data (≥ 32 KiB): library median 0.795 over 74 cells, both runs alike; CLI single-threaded 16 MiB-1 GiB −16% to −20% in all three runs; mixed file tree −10%. No proof. 0.8's claim is that every assembly kernel is proved (#166, the quality manual, ANNOUNCE). These kernels (k32/p32/p16) are not in tools/verify, and have no mutation coverage. Shipping needs proofs, or a narrower claim.
Calls below the pool's split gain the same: multithreaded calls of 64-256 KiB run on one thread, −12% to −27%. Collections −5% to −16% (Nix −16% one thread, −15% every thread). No gain from SMT. With the core's other thread busy, each wide thread takes 17-18% more time than the old kernel's (0.184 against 0.157 ns/B); one core with two threads does ×1.10 the work of one, against ×1.62 for the old kernel. Two copies of the wide kernel compete for the same core resources (dispatch slots, PipelineL1).
No cost on paths it doesn't take: small messages, batches of 64 B messages and Merkle trees match the same-code control (medians 0.997-1.000). Small cost when the pool runs every thread on bulk data: library mt 32-128 MiB +1.6% to +3.1%, with 0 of 12 pairs faster in both runs (the ablation shows it's the kernel's own); CLI warm 1 GiB with every thread +1.8%, +5.2%, +6.5% (never judged slower); b3sum's pool on 1 GiB in the energy run, 12% more time.
Less energy with a core to itself: one thread hashing 1 GiB, 7% less time and 5% less package energy per GiB; one process per core, −4%. More energy with every thread busy: b3sum's default pool on 1 GiB, +9% package and +16% core energy per GiB; 48 single-threaded processes, +0.5% package and +5.5% core. Its own cores draw more power (+13% single-threaded).
Cold files, every thread: CLI 1 MiB from storage −19% to −24% in all three runs. A small per-process cost: "1000 × 16 KiB, a process each" +1.2% to +2.3% in all six CLI runs (about 5 µs a process: three more startup self-test cases, more code). Small files lean +2-3% without being judged slower.
Correct on this machine by every suite here, including the guard-page tests (any out-of-bounds read or write faults), and the startup self-test, which checks the three entry points on every AVX-512 start. One machine. It would run on every Linux AVX-512 CPU: Intel Xeon (Skylake-SP to Granite Rapids), Ice/Tiger/Rocket Lake clients, and AMD Zen 4, which executes 512-bit instructions in two halves and may well run it slower than the old kernel. None of these has been measured. Nearly all of them have SMT.
Small and generated: 7.2 KB of machine code (k32 and p32 share one body; p16 2.7 KB), about 11% of the fork's x86 assembly; 1,242 lines generated by a 372-line generator; Linux only, so no other assembler form is needed (Windows isn't supported, #169). More to maintain: another generator, a second AVX-512 dispatch path (groups of 32 chunks and 16 parents, the old kernel for the rest), a degree of 32 on Linux (buffers sized by it), and a longer startup self-test chain.
A separable gain in its tree-thread budget: multithreaded 512 KiB −20% to −23% and 1 MiB −5% (the ablation shows this is the budget, not the kernel: one 128 KiB piece a participant, so fewer threads are woken for a medium tree). The budget has its own small cost: mt after a pause, 2-3 MiB +3.0% to +3.6% at 12 pairs (judged slower once at 3 MiB; +0.9-1.0% at 16 fresh pairs). It should be judged on its own, and could apply to the old kernel too.

A possible middle way (not measured)

Both costs come from many wide threads sharing cores. The wide kernel could hash only on the calling thread, with the pool's workers keeping the old kernel. That would keep the single-thread wins (one-shots, streams, lent messages, collections, every call below the split) and avoid the all-core cost. a5e1e18 already did this for pooled group work. It's a small dispatch change, but it would need its own measurement.
